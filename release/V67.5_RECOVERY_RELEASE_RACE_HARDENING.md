# V67.5 — Recovery Release Race Hardening

## Objective

Harden the autonomous recovery boundary against concurrent recovery coordinators,
retries, worker claims, and crash-window races.

## Contract

Recovery release is a single transactional state transition:

`failed -> pending -> processing`

Only the database release function may perform `failed -> pending` for an
AUTO_RECOVER plan. It must verify:

- persisted recovery plan exists and is `auto_recover`;
- plan authority is `none`;
- plan workspace matches the request;
- persisted exception belongs to the same workspace and intent;
- the failed outbox row is locked with `FOR UPDATE`;
- the retry attempt budget remains available.

The exception state is advanced to `recovery_planned` in the same transaction.
If the transaction rolls back, the control-plane state cannot claim that release
succeeded.

## Race guarantees

### Two recovery coordinators

Both may observe the same deterministic recovery plan, but the plan row is
serialized with `FOR UPDATE`. The first transaction that successfully releases
the failed outbox row wins. A later coordinator sees that the row is no longer
`failed` and returns `false`.

### Recovery versus worker claim

The worker only claims `pending` work. Recovery only releases `failed` work.
The failed-row lock serializes the transition so recovery cannot reset a row
that has already moved into live processing.

### Recovery retry after worker claim

A stale coordinator cannot change `processing`, `succeeded`, `failed`-with-newer
state, or other non-failed states back to `pending`.

### Crash window

If recovery commits `failed -> pending` and the process crashes immediately,
the durable outbox remains pending and can be claimed later. Execution
idempotency remains governed by the Execution Ledger, so recovery does not create
a second provider authority path.

## Boundary statement

V67.5 does not authorize new business actions. It only hardens the transition
from an already-governed failed Action Outbox intent back to a pending retry
when the persisted recovery plan explicitly permits autonomous recovery.

High-risk, irreversible, reconciliation-required, policy-blocked, and review
required paths remain outside autonomous retry.
