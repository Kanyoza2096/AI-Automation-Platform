# V67.1 — Autonomous Recovery Runtime Integration

## Status
Implemented and tested.

## Purpose
V67.1 connects the V67 recovery governance model to the real Action Outbox lifecycle without creating a second execution path.

## Runtime path

```text
ActionOutboxWorker
  -> ActionKernel.process_outbox_row()
  -> ExternalActionExecutor / ExecutionLedger
  -> terminal failure or uncertainty
  -> RecoveryCoordinator
  -> durable exception + recovery plan
  -> AUTO_RECOVER only
       -> release_action_outbox_for_recovery()
       -> status pending + bounded backoff
       -> ActionOutboxWorker claims again
       -> ActionKernel executes
```

## Safety invariants

1. Recovery never invokes a provider directly.
2. Recovery never writes a successful execution receipt.
3. Only `AUTO_RECOVER` plans may request a release.
4. The database release function requires a persisted matching plan, workspace, intent, and `authority = none`.
5. Release is race-safe because the database requires the intent to still be terminal `failed`.
6. The recovery plan's maximum attempt budget is checked against the durable outbox attempt count.
7. Uncertain/reconciliation-required outcomes do not enter the retry release path.
8. Actions must explicitly opt into `autonomous_retryable`; the presence of an idempotency key alone is not treated as proof of retry safety.
9. High-risk, irreversible, authentication, policy, validation, unknown, partial, and uncertain outcomes remain governed/reconciled rather than blindly retried.
10. Repeated transient failures are quarantined after the bounded budget.

## Explicit retry-safe actions

The initial bounded retry set is deliberately narrow and consists of CRM operations whose contracts are explicitly marked `autonomous_retryable=True`. New actions must opt in deliberately after an idempotency/reconciliation review.
