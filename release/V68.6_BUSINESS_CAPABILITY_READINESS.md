# V68.6 — Business Capability Readiness & Operating Surface

## Purpose

V68.6 connects the declarative business-workflow catalog to declared runtime capability state. It answers whether a catalog workflow can be operated in a workspace now, without creating another execution engine.

## Boundary

This phase is advisory/readiness-only. It does not execute providers, approve work, mutate policy, or bypass the Action Kernel, Decision Policy, Council, outbox, execution ledger, or recovery plane.

## Readiness states

- `ready`: workflow is admitted by the autonomy envelope and required runtime capabilities are ready.
- `review_required`: workflow is otherwise ready but existing governance requires human/Council review (for example high-impact work).
- `blocked`: missing capability, workspace mismatch, unknown workflow, or envelope/admission failure prevents operation.
- `unknown`: a required capability is explicitly unknown/degraded; KDO does not optimistically assume readiness.

## Important distinction

Catalog requirements mentioning approval are governance requirements, not runtime-provider capabilities. They are therefore not treated as missing integrations. A high-impact workflow can be operationally ready while still requiring the existing approval path.

## Capability vocabulary

The module normalizes catalog requirements into stable readiness keys such as `crm`, `whatsapp`, `notification`, `workspace_reporting`, and event-source capabilities. These are declared status inputs, not provider credentials or execution handles.

## Safety invariants

Every readiness result has:

- `authority = none`
- `execution_effect = none`
- `approval_effect = none`
- `policy_effect = none`

The defense-in-depth assertion rejects execution/bypass metadata including direct provider execution, Action Kernel bypass, Council bypass, and auto-approval.
