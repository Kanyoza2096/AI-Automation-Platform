# V67.8 — Multi-Process Chaos Pre-Staging

## Purpose

V67.8 adds a deterministic multi-process chaos harness that exercises the
critical ownership and uncertainty invariants before live staging chaos is run.
It is deliberately not presented as production certification.

## Scenarios

1. Four independent worker processes race for one pending outbox item.
2. Only one process may obtain the atomic claim.
3. Provider invocation occurs at most once in the race harness.
4. Provider success followed by process death before receipt persistence becomes
   `reconciliation_required`, never an ordinary retryable failure.
5. A crash before provider invocation produces no external side effect.

## Why this matters

V67 now distinguishes these states:

`pending -> processing -> provider side effect -> durable receipt -> succeeded`

versus:

`pending -> processing -> provider side effect -> process death -> reconciliation_required`

The second path must never be silently converted into a blind retry because the
remote provider may already have accepted the request.

## Staging gate still required

The harness is a pre-staging certification layer. V68 still requires a real
multi-process/staging exercise against the authoritative database and provider
sandbox, including:

- independent worker processes/containers;
- real `claim_action_outbox` and lease renewal RPCs;
- real `begin_external_execution` / `renew_external_execution` / completion RPCs;
- database/network interruption;
- worker termination at controlled crash points;
- provider latency and provider acknowledgement ambiguity;
- reconciliation evidence from the provider;
- duplicate-side-effect verification using provider idempotency keys.
