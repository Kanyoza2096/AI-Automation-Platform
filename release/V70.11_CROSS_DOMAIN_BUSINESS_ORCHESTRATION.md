# V70.11 — Cross-Domain Business Orchestration

## Purpose
Coordinate explicit governed workflows across customer, sales, operations and management domains without creating a second execution or governance plane.

## Architecture
Business Event → explicit scenario → ordered governed workflow steps → BusinessOperatingLayer → existing Action Kernel / durable outbox / connectors → verified result.

## Safety invariants
- AI does not manufacture executable authority.
- Every orchestration step must exist in the Business Automation Catalog.
- Every step must be inside the registered objective's workflow scope.
- Tenant mismatch is rejected.
- Duplicate source events are rejected.
- Terminal orchestration states cannot be executed again.
- No direct provider, connector, Action Kernel, or database side effects are performed by the orchestration service.
- No implicit compensation/rollback is attempted; consequential compensation must itself be an explicit governed workflow.

## Explicit scenarios
- customer.retention-risk → sales.retention-attention → management.plan-risk-escalation
- customer.expansion-opportunity → sales.expansion-attention → management.plan-attention
- operations.sla-breach → operations.failed-work-escalation → management.plan-risk-escalation
- business.plan.risk → management.plan-risk-escalation

## Persistence
`migrations/086_v70_11_cross_domain_business_orchestration.sql` establishes tenant-scoped durable orchestration state and source-event uniqueness. Runtime adapter remains intentionally separate so production persistence can converge on the existing durable infrastructure rather than creating a new repository plane.
