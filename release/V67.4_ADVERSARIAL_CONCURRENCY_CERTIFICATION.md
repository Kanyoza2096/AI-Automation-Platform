# V67.4 — Adversarial Concurrency & Ownership Certification

## Objective

Harden the autonomous recovery runtime against the failure modes that are most
likely to produce duplicate external side effects: slow handlers, lease expiry,
stale ownership tokens, concurrent execution ownership, and terminal-finalization
confusion.

## Changes

### 1. Production heartbeat seam

`ActionOutboxWorker` now exposes one production heartbeat implementation instead
of a duplicate test-only heartbeat. `_renew_lease()` performs the fenced RPC and
`_heartbeat()` owns the renewal loop.

The renewal is fenced by:

- `intent_id`
- `workspace_id`
- `lease_token`
- live `processing` status
- bounded lease duration

A rejected heartbeat never grants authority and never triggers a second provider
execution. Existing Execution Ledger and outbox lease fencing remain authoritative.

### 2. Slow-handler race protection

Adversarial tests model worker A holding a slow action while worker B repeatedly
attempts to claim the same outbox work. Heartbeat renewal prevents the simulated
lease from becoming claimable while A remains the owner.

### 3. `in_progress` ownership correction

A second worker can legitimately discover that the Execution Ledger is already
owned by another live worker for the same idempotency key. `in_progress` is now
treated as a non-terminal ownership signal.

The Action Kernel no longer attempts `finalize_action_outbox(..., p_status='in_progress')`,
because the durable finalizer intentionally accepts terminal states only. This
prevents a false worker exception/reconciliation transition caused solely by a
live execution owner.

### 4. Stale-token fencing

Tests verify that renewal and finalization require the original lease token and
that finalization also requires `processing` state. A stale worker therefore cannot
renew or finalize a row after ownership has moved elsewhere.
