# V67.7 — Control-Plane Crash Consistency & Recovery Truthfulness

## Purpose

V67.7 closes a subtle recovery-state inconsistency discovered during adversarial review.

Previously, `RecoveryCoordinator._persist()` marked an exception `recovery_planned`
before the transactional recovery-release RPC had actually won the `failed -> pending`
transition. A crash or a competing coordinator could therefore leave the control plane
claiming that recovery was planned even though the action remained failed or had already
been claimed by another worker.

## Correct state machine

```text
failure observed
      |
      v
exception = open + durable recovery plan
      |
      | release RPC
      v
  +---+--------------------+
  |                        |
  v                        v
failed -> pending       release loses race
exception ->             exception remains open
recovery_planned         for safe retry/review
  |
  v
worker claims pending
  |
  v
processing
```

The exception state is now advanced to `recovery_planned` only inside the same database
transaction that successfully changes the Action Outbox row from `failed` to `pending`.

## Invariants

1. A durable recovery plan is evidence, not execution authority.
2. `recovery_planned` means the outbox release actually won.
3. A crash between plan persistence and release leaves truthful `open` state.
4. A release race cannot reset `processing` work.
5. Retried coordinators may safely attempt the release again.
6. External execution remains exclusively behind Action Kernel + Execution Ledger.
7. Uncertain external state is never converted into an autonomous retry.

multiple worker processes, provider latency/failure injection, restart tests, and
reconciliation evidence.
