# V67.6 — Crash Consistency & Execution Lease Hardening

## Objective

Close the long-provider and crash-window gap between the Action Outbox lease and
the durable Execution Ledger lease.

## Implemented

- `ExternalActionExecutor` now maintains a heartbeat for the durable Execution
  Ledger while a provider operation is running.
- A failed execution-lease renewal never claims that the provider was cancelled.
  Completion remains fenced by the Execution Ledger worker/lease.
- If completion loses ownership after a provider may have executed, the result
  remains `uncertain` and reconciliation is required.
- The in-memory execution ledger test adapter now mirrors production semantics:
  an expired in-flight lease becomes `uncertain` rather than being reclaimed
  blindly.
- Existing PostgreSQL `renew_external_execution` remains the authoritative
  renewal boundary; no new side-effect authority is introduced.

## Crash invariants

1. Provider success without a durable receipt is **not** converted to ordinary
   failure.
2. An expired execution lease is **UNCERTAIN**, not retryable by itself.
3. A live execution lease is not concurrently executable by another worker.
4. A stale worker cannot complete after ownership is lost.
5. Recovery can only proceed through the existing governed Action Outbox → Action
   Kernel path.
6. No heartbeat failure grants execution authority or cancels a remote request.

## Certification scope

Focused tests cover expired-lease quarantine, active lease renewal, renewal
failure behavior, renewal RPC fencing, and completion ownership fencing.

This is runtime hardening and adversarial unit certification, not a claim of
production certification. Live staging evidence with real PostgreSQL RPCs,
multiple worker processes, provider latency, and process termination remains a
V68 production-autonomy gate.
