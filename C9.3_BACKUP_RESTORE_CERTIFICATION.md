# C9.3 — Backup / Restore Certification

## Implemented contract

KDO now has a fail-closed backup/restore certification harness at
`scripts/backup_restore_certification.py`.

A real certification requires:

1. a real PostgreSQL source database;
2. a **separate isolated restore database**;
3. a custom-format `pg_dump` artifact;
4. `pg_restore --exit-on-error` success;
5. a deterministic verification query returning the same value before and after restore;
6. SHA-256 evidence for the backup artifact;
7. measured backup and restore duration.

The harness never writes database credentials to the evidence manifest. DSNs
are redacted before evidence is persisted.

## Live staging run

Inspect an existing dump:

```bash
python scripts/backup_restore_certification.py \
  --inspect \
  --backup-file /path/to/kdo.dump
```

Run the actual certification against a disposable restore database:

```bash
DATABASE_URL='postgresql://...' \
KDO_RESTORE_DSN='postgresql://.../kdo_restore_cert' \
KDO_BACKUP_VERIFY_QUERY="SELECT count(*) FROM public.workspaces" \
python scripts/backup_restore_certification.py \
  --live \
  --backup-file /tmp/kdo-c9.3.dump \
  --evidence /tmp/kdo-c9.3-evidence.json
```

**Never point `KDO_RESTORE_DSN` at production.** The restore target must be
isolated and disposable.

## Operational limits

Passing this harness proves database backup/restore for the selected staging
verification query. It does not by itself prove:

- Google Drive retention/deletion protection;
- point-in-time recovery;
- cross-region disaster recovery;
- cloud-provider durability;
- achieved RPO/RTO across repeated timed incidents;
- real PostgreSQL concurrency or provider execution.

Those remain staging/operations evidence.
