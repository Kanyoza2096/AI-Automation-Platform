# KDO AI Engineering Vertical — Completion and Staging Guide

## Architecture delivered in repository

The engineering vertical now contains role selection and gateway adapters, dependency-aware orchestration, scoped task contracts and SQLite development persistence, team event logging, bounded command-runner primitives, explicit tool policy checks, Council-to-Action-Kernel governance bridge, durable receipt verification, and a read-only receipt-schema preflight. Local regression coverage exercises the interfaces using deterministic fixtures.

These components are not interchangeable with deployed infrastructure. The SQLite task repository and team event store are development/local stores; the bounded command runner is not an OS/container security sandbox; the gateway role adapters do not prove a live provider is reachable; and an in-memory Action Kernel test does not prove durable production execution.

## Safe staging deployment

1. Create an isolated staging project/database. Do not reuse production credentials or production data.
2. Configure database migrations/policies for `action_outbox` and `external_execution_ledger` from the authoritative KDO schema. Confirm the required receipt columns exist and are indexed by their lookup keys.
3. Create `deployment/staging/.env.staging` from `.env.staging.example`. Inject actual staging secrets via a secret manager or secure operator channel. Never commit the populated file.
4. From the repository root, run `python scripts/kdo_engineering_staging_gate.py`. This is configuration-only; it prints presence and validation results, never secret values.
5. Run `python scripts/kdo_engineering_staging_gate.py --live-read-only`. This performs zero-row schema/read-access queries through the RLS-aware anon client. A successful result is not proof of tenant-specific row visibility or full lifecycle readiness; the application server’s privileged receipt-read role must be separately least-privilege reviewed.
6. Start the isolated staging service with `docker compose -f deployment/staging/docker-compose.yml up --build -d`.
7. Verify `http://127.0.0.1:10001/health/live` and `/health/ready` from the host. Do not expose the staging port publicly without TLS, authentication, ingress policy, and an approved threat model.
8. Run the regression suite: `pytest -q tests/engineering_vertical tests/reliability/test_execution_ledger.py tests/test_condition_engine_council_approval_fence.py`.

## Required staging acceptance evidence

- [ ] Real staging Council decision IDs are generated by the deployed Council, and denial blocks execution.
- [ ] Action Kernel uses durable database-backed execution records, not `allow_in_memory=True`.
- [ ] Receipt verifier confirms one matching `action_outbox` row and one matching `external_execution_ledger` row for the exact task, tenant, workspace, decision, action, intent, and execution identity.
- [ ] Cross-tenant and cross-workspace reads are denied under the actual runtime database role. Use two disposable staging tenants and preserve the negative-test results.
- [ ] Replaying an idempotency key does not repeat a consequential provider side effect.
- [ ] Simulated timeout after provider submission yields uncertain/reconciliation-required until authoritative read-back resolves it.
- [ ] Worker crash/restart, stale lease, and concurrent claim tests pass against the actual durable worker backend.
- [ ] Agent code execution is isolated in a disposable sandbox with CPU, memory, time, filesystem, and network restrictions; production secrets are absent from the child process.
- [ ] Independent reviewer identity differs from implementer; test evidence is machine-collected; release authorization is a separate human/governance decision.
- [ ] Logs, trace IDs, canonical receipt IDs, database migration version, image digest, and test reports are retained as release evidence.

## Deployment boundary and blockers

This repository package can prepare and validate a staging deployment configuration, but it cannot deploy to an external cloud account without authorized credentials, a staging endpoint, and an operator-approved target. No live staging deployment is claimed by the local test results. The compose target binds to loopback for initial validation and disables autonomous Guardian behavior by default.

Do not mark production ready until the acceptance evidence above is collected from the actual staging environment and reviewed. A green local test suite is necessary, not sufficient.
